## 1. 维护边界与部署定位

现有部署记录使用 Railway 项目 `self-learning-agent`、服务 `study-agent`，访问地址为 [书内学习助手](https://study-agent-production-5c45.up.railway.app)。本轮未查询线上状态，执行操作前必须在平台确认项目、环境、服务、部署版本及卷，不能仅凭本地 CLI 曾经链接过就上传。

当前代码要求 1 个服务副本、1 个 Gunicorn worker、8 个 gthread 请求线程。数据库、锁与后台任务未按多进程设计；增加 worker/副本前需要外部任务协调与存储设计，不是简单改一个部署参数。

只读调查也有例外：`GET /api/logs` 会清理过期应用日志；`create_app()` 会初始化/迁移数据库、标记中断索引、播种测试码/内置书并启动统计。不要在生产数据目录额外创建应用实例来“只查一下数据库”。

## 2. 发布与回滚

### 2.1 发布前

1. 确认目标 Railway 项目、环境和服务，检查持久卷挂载 `/data`，与 `STUDY_DATA_DIR` 一致。`railway.toml` 没有声明或自动创建卷。
2. 审查工作区变更和上传范围，排除 `.env`、测试码、数据文件、私人素材。当前 Docker 白名单只交付应用源码、web、依赖和内置书；docs 不进入运行镜像。
3. 核对持久 `STUDY_SECRET_KEY`、HTTPS Secure Cookie、注册策略、主备模型与 embedding 配置，密钥只填写 Railway Variables。
4. 涉及 schema、教材内容、分块/向量变更或测试码启用时，先完成一致性备份并写明可能删除的数据，获得维护授权。
5. 由开发者按开发说明完成所需验证；记录实际执行的验证，不把旧报告当本次结果。发布前避免有索引正在运行。

### 2.2 发布方式

项目曾使用 Railway CLI 从本地工作区直接上传。以下命令仅供已安装、已登录且正确链接的维护终端执行，不会自动创建或选择正确环境：

```powershell
railway status
railway up --service study-agent --ci
```

确认 status 指向目标后才执行第二行。直传的是当前工作区，不要求已提交 Git，因此可能包含未提交的运行代码；应记录发布所对应的源码快照或校验值以便回滚。不要假设“Git 没变就没有发布差异”。

若使用 Git 集成，另行核对仓库、分支和触发方式，避免 Git 自动部署与 CLI 直传相互覆盖。发布授权不等于提交或推送 Git 授权。

Git Bash 中需要传 `/data` 等容器路径参数时，注意 MSYS 路径转换，可按实际命令使用 `MSYS_NO_PATHCONV=1`；PowerShell 不需要这个前缀。不要把任一工具安装目录写进项目配置。

实际启动命令以 [Dockerfile](../Dockerfile) 为准：

```text
gunicorn 'study.app:create_app()' --bind 0.0.0.0:${PORT:-8080} --workers 1 --worker-class gthread --threads 8 --timeout 180 --graceful-timeout 30 --access-logfile - --error-logfile -
```

[railway.toml](../railway.toml) 选择 Dockerfile、`/health`、120 秒健康检查、失败重启最多 5 次和单副本。CLI 或平台若提示配置字段弃用，应查当前平台说明并单独评估迁移，不要忽略告警或在普通功能发布中盲改配置。

### 2.3 发布后检查

| 检查 | 判断依据 |
| --- | --- |
| 容器与数据库 | `/health` 为 200；仅说明数据库连接可查询，不说明模型可用 |
| 持久化 | 卷路径正确，已有账户与对话仍在，数据未落临时容器目录 |
| 教材 | 已有书 ready；新书可能仍 queued/indexing，继续观察状态和日志 |
| 账户安全 | 登录、Cookie、CSRF 正常；不应为验收打开公开注册 |
| 模型 | 使用获准的测试账户提问，消费完整 SSE，检查最终 answer 或 error |
| 引用与导航 | 引用能打开对应正文，前后分块不跨书，语义失败仍可读原文 |
| 反馈 | 测试提交后刷新历史验证当前状态；统计需等完整周期或在隔离副本验证 |

在线问答会产生费用，注册会消耗测试码并写入账户；这些不是纯只读探测。避免用真实用户的会话作为随意测试场地。

### 2.4 回滚

代码回滚不等于数据回滚。内置教材旧版本与卷中源文件不同也会触发重建并清对话；较旧代码还可能不兼容已迁移 schema。回滚前对比目标代码、schema 和内置书内容，确定是否需要配套恢复备份。

不要默认使用破坏性的 Git reset、删除卷或覆盖数据库。需要恢复时先停写、保留当前完整快照，再按下一节恢复一致的数据版本。

## 3. 备份与恢复

### 3.1 应备份什么

备份整个 `STUDY_DATA_DIR`，包括数据库、对应源文件和存在的本地 `.session-secret`。生产 Variables 中的密钥和服务配置需要单独受控保存，不能打进公开文档或 Git。

SQLite 开启 WAL，运行中只复制 `study.sqlite3` 可能漏掉已提交数据。不同时间分别复制主库、WAL、SHM 也不保证一致性。反馈归档“不按三天删除”不等于它有异地备份。

### 3.2 推荐备份流程

1. 选维护窗口，暂停写请求，等待索引、问答及后台任务结束，停止应用。仅关闭普通注册不能暂停现有用户写入。
2. 在无写入进程的情况下，对数据目录做完整一致性快照/复制，并保留备份时间、应用版本、内置书版本、模型配置名称和文件校验值，不记录密钥明文。
3. 如必须在线备份数据库，使用 SQLite Backup API 或经验证的快照机制；同时协调 sources 的版本，不能只备份数据库却遗漏其引用的文件。
4. 在隔离副本以只读方式检查 `PRAGMA integrity_check;` 和 `PRAGMA foreign_key_check;`，核对书数量、消息数量、源文件是否齐全。
5. 备份加密、限制访问，并定期在隔离环境演练恢复。不要仅因备份任务显示成功就认定可恢复。

### 3.3 恢复流程

停服后先备份现状，隔离旧数据库及其 WAL/SHM，按同一快照恢复数据库和 sources，避免旧 sidecar 与新数据库混用。恢复路径应继续满足库中 source_path 的相对定位，并核对目录写入权限。

启动前审查目标代码与内置教材、测试码配置：启动过程可能执行迁移、内置书重建清会话、旧共享测试账户退役和统计补算。不要在未经审查的恢复副本上直接连生产配置启动。

最后先在隔离环境核对历史、引用与源文件，再恢复服务并做有限验收。更换会话密钥会使旧登录 Cookie 失效，用户需重新登录；不会自动重置账户密码。

## 4. 教材与向量索引维护

### 4.1 添加新的内置教材

运行时接受 `.md/.markdown/.txt/.docx`。DOCX 在服务端用标准库转换为 Markdown：提取正文段落（跳过文本框重复内容），按 Word 样式（heading/outlineLvl）或启发式规则（第N编/章/节、X.Y/X.Y.Z 编号，短行、无句末标点、不带页码）识别标题；图片、表格结构与分节页脚脚注不做专门处理，页眉仅按“疑似标题”规则排除。对大部头扫描教材，离线定制转换（见各 Asset 目录脚本）通常优于通用导入，先检查再上传。

将确认有使用及分发权利的源文件放入 `builtin_books/` 直属目录，再发布包含该文件的镜像。启动播种将源文件复制到共享所有者 builtin 下并排队索引；无需也不应通过普通用户上传来冒充内置书。源文件会随镜像分发，需审查其内容与版权。

确认书架出现“内置”、索引状态 ready、章节合理、能得到真实引用，并确认普通用户不能重建/删除/下载内置原文件。索引线程只有一个，新增多本书时等待队列逐本处理；不要因健康检查已通过就反复重启。

当前内置目录包含《行政诉讼法》《刑事诉讼法通义》《民法 第八版 魏振瀛》《利维坦》《宪法学》五本。《宪法学》由三本宪法教材按 第二版→讲义→新时代 顺序合并为单本（各保留自己的 h1，约 2.58 MB，索引后 210 节 / 1079 段）。《民法》已按 1–200、201–400、401–600、601–800、801–910 的文件顺序转换合并，包含七编、四十八章和 240 个节标题，Markdown 约 2.45 MB。可提取的正文、文内脚注和前后记按顺序保留；分节页脚中的 25 条脚注也按分节锚点恢复（11 条为被截断脚注的续文，直接接续前段；14 条为完整脚注，插入分节末尾）；两处被 OCR 拆成两段的小节标题已合并；分卷中两处被截断的段落已接续；图片没有转录，原 OCR 错误未作内容性修订。

曾用 `railway ssh` 在线上删除合并前的旧宪法书：删除 books 行时开启外键级联（chunks、会话与批注一并删除），并按 book id 清理 `/data/sources/builtin/<book-id>.md` 孤儿源文件——source_path 相对 /data 按 book id 命名，不是按标题命名，按标题匹配清理无效。同类清理应先备份并在隔离副本演练。

本地转换脚本和 `conversion-report.json` 保存在对应 Asset 素材目录，报告记录各源文件及合并文件的 SHA-256、章节数和字符顺序校验。该目录仍被忽略，不随镜像交付；只有 `builtin_books/` 下的成品 Markdown 进入镜像。目录条目保持为正文文本，不被误当成正文章节；节标题数是实际识别数，不承诺 OCR 标题完全无误。

### 4.2 更新、改名与移除的不同影响

| 操作/状态 | 当前播种行为 |
| --- | --- |
| 标题相同、ready、源文件字节一致 | 跳过，不重建 |
| 标题相同但内容变化、源缺失或不是 ready | 重建已有书，先删除该书所有用户会话、消息与批注 |
| 修改文件名导致标题变化 | 通常按新书新增；不是原书重命名 |
| 从镜像移除文件 | 不会自动删除卷内旧共享书 |
| 只改解析器或向量配置，源文件仍相同且 ready | 不会自动重建 |

用户私有书可通过重新索引接口重建，也会清除对应会话，前端有确认提示。内置书没有普通用户可用的强制重建接口；需在备份和授权后设计受控维护操作。不要靠改空格或删除数据库记录来绕过这一缺口。

反馈表没有随对话级联删除；重建后可能留下引用旧消息的反馈记录，归档仍保留问题片段。维护时应区分“历史反馈留存”和“可完整复现的回答样本”。

### 4.3 更换向量服务

先检查服务实际支持的模型名、响应结构、维度及部署区域可达性，再修改配置。只验证 `/models` 列表不能证明 embeddings 可用；实际 embedding 探测会发送输入文本，应使用获准的非敏感内容。

向量空间指纹包含 endpoint、模型名和维度。更换其中任一项后旧向量可能全部不再参与检索；同名同维服务更换权重也应评估重建。`embedding_configured=true` 只表示字段完整，不证明本书已拥有匹配空间的向量。

自有书按受控重新索引流程处理；内置书需单独维护计划，明确清除所有用户书内会话的后果。服务故障期间词法/FTS 降级可继续工作，不应为掩盖 degraded 标志随意混用旧向量。

## 5. 账户与测试码

测试码来自 `STUDY_TEST_CODES`，启动时 `INSERT OR IGNORE` 写入数据库；每个码只能绑定一个自选用户名/密码账户，绑定与创建用户在同一事务中完成。重复用户名不会消耗该次测试码，已绑定码不可重复使用。线上码池曾于 2026-09-18 扩充至 15 个（当时 7 个未绑定）；当前余量以 `test_codes` 表实际查询为准。

测试码注册与 BYO（自带 API Key）注册是两条通道。无测试码注册要求用户填写 8–400 字符的个人 API Key，该 Key 只替换主模型的站点密钥（备用模型仍用部署者密钥），存储于 `users.api_key`，任何接口都不回显。`STUDY_REGISTRATION_OPEN=0` 同时关闭两条注册通道；数据库中未使用码为零且注册关闭时，前端隐藏注册入口。设置面板可随时更新或清除个人 Key。

重要边界：

- 从环境变量移除测试码不会撤销数据库中的码，重启也不会清绑定。增加码可在受控 Variables 配置后启动播种，撤销则没有现成管理 API。
- 若要真正停用测试码注册，需要单独授权的数据库维护方案，并同步处理环境中的播种列表；仅删除数据库未绑定码而保留环境配置会在后续启动再次插入。
- 只要存在非空有效测试码配置，每次启动都会按代码中的固定用户名 `beta01`–`beta05` 删除匹配账户、书籍、会话及日志；没有检查账户来源或创建时间，也不是仅执行一次的旧账户迁移。注册端点未保留这些名字，后来新注册的同名账户也会在后续启动时被删除，应避免使用。源文件与反馈归档没有一起清理，不能将其当完整隐私删除流程。

仅检查总量时，在现有授权的只读数据库连接中执行下列 SQL，不导出真实码、密码哈希或用户清单：

```sql
SELECT COUNT(*) AS total,
       COALESCE(SUM(CASE WHEN bound_username = '' THEN 1 ELSE 0 END), 0) AS available,
       COALESCE(SUM(CASE WHEN bound_username <> '' THEN 1 ELSE 0 END), 0) AS bound
FROM test_codes;
```

没有密码找回、邮件验证、管理员账户控制台或现成测试码解绑功能。支持请求应通过受控维护流程处理，不修改 CSRF 或公开数据库来简化操作。

## 6. 日志、反馈和改进数据

### 6.1 两类日志

网页“设置”读取 `/api/logs`，最多 200 条。`app_logs` 在读取和新增时清理超过三天的数据，不保证到期瞬间由独立清理任务删除。每条 detail 最多 2000 字。

Gunicorn/Python 的 stdout/stderr 由部署平台收集，其保留周期不受应用这三天设置控制。模型解析错误日志可能含输出片段，问答日志包含问题片段，登录失败包含用户名；转发前必须脱敏。

### 6.2 反馈存储分工

| 存储 | 能回答的问题 | 不应怎样解释 |
| --- | --- | --- |
| `feedback` | 当前每条答案是满意还是不满意、当前原因 | created_at 不是最后改评时间；删除会话后的残留行需辨别 |
| `feedback_archive` | 每次提交、改评、撤销的时间与原因 | 不是去重答案数，没有完整回答/证据快照 |
| `feedback_stats` | 完整三日周期内提交了多少满意、不满意、撤销 | 不是用户数或最终净满意率 |
| `app_logs` | 最近操作及失败的快速排查 | 不是长期评测数据源，也不是完整审计账本 |

不满意预设为“没找到相关内容”“回答不准确”“引用与问题不符”“太简略”，也可填写其他原因或跳过。后端最多保留 200 字；归档问题最多 120 字。撤销仍记入 archive，但不写非零评价的 answer_feedback 操作日志。

归档机制上线前已有的当前评价仍可能保存在 feedback，但没有自动补录历史点击。归档、统计不受三天日志清理影响，当前没有自动过期策略；需要规划容量、隐私留存和备份。

### 6.3 三日汇总的准确时间语义

汇总从第一条归档事件的 UTC 时间开始，每个窗口为 `[开始, 开始+72小时)`，不是自然日零点对齐。每次应用启动及每 6 小时检查已关闭的周期，正常运行时周期关闭到落表可能还需等待最多约 6 小时；失败或停机可更久。启动会补算完整窗口，可能包括空窗口。

汇总全局统计 up/down/clears，并把差评原因和问题各按次数保存 Top 10 JSON；相同问题截断后可能合并。系统日志只展示数量，没有独立报表页面、邮件推送或定时任务平台配置。不要额外再配置一套三日 cron 造成重复职责。

通过授权的只读数据库连接或备份副本检查：

```sql
SELECT period_start, period_end, up, down, clears, reasons, questions
FROM feedback_stats
ORDER BY period_end DESC
LIMIT 20;

SELECT MIN(created_at) AS first_event,
       MAX(created_at) AS latest_event,
       COUNT(*) AS events
FROM feedback_archive;
```

SQL 结果可能含问题和原因，应限制访问。数据库 ISO 时间带 UTC 偏移；展示给用户前明确时区，不把 UTC 时间直接称作用户当地凌晨。

若想查看当前仍存在的回答的最终评价分布，可通过关联 messages 排除已删回答残留：

```sql
SELECT f.rating, COUNT(*) AS answers
FROM feedback AS f
JOIN messages AS m ON m.id = f.message_id AND m.owner_id = f.owner_id
GROUP BY f.rating;
```

以上查询仅用于受控维护，不应新增为所有用户可读的全局接口。Python sqlite3 只读连接应使用正确编码的文件 URI 加 `?mode=ro`，并传入 `uri=True`；可由 `Path(database_path).resolve().as_uri()` 构造 URI 前缀。不要用创建第二个 Flask 应用代替只读连接。

### 6.4 人工改进闭环

建议按周期先区分检索漏召回、回答错误、引用不匹配、上下文展示不足和过于简略，再从仍存在的 messages.payload 核对原答案、引用和诊断。缺少完整上下文的归档只作线索，不直接当高质量训练样本。

经授权脱敏后建立固定评测集，记录预期证据、书版本、参数与模型，离线比较改动效果。现有统计不会自动修改提示词、检索参数或模型权重；“案例上下文不完整”也可能只是面板阅读能力问题，不应一律扩大生成上下文。

## 7. 故障排查

| 现象 | 优先检查 | 避免的误操作 |
| --- | --- | --- |
| `/health` 成功但不能提问 | 书状态、主备模型、SSE 最终 error、应用与平台日志 | 不把 health 当模型连通性检查 |
| 401 | 登录是否成功、Cookie 会话是否保持、HTTPS 与 Secure 属性、密钥是否轮换 | 不共享用户 Cookie 或改为不安全生产 Cookie |
| 403“安全凭证过期” | 先 auth/me、同一 CookieJar、写请求 CSRF、新登录 token 是否更新 | 不关闭 CSRF、不无证据归因于 UA 或缓存 |
| GET 端点意外 403 | 脚本是否误传 data 变成 POST；方法和 body 应显式设置 | 不用含糊的位置参数传 token；读请求不要附 JSON body |
| 内置书操作 403 | 是否尝试删除、重建或下载内置源文件 | 不绕过 require_own_book |
| 模型 404 | BASE_URL 是否重复 `/v1` 或 `/chat/completions`，供应商路径是否完整 | 不先更换无关凭据 |
| 429 | 应用槽位/频率限制，或上游额度不足，检查两者错误来源 | 不并发重试扩大压力；不保证备用必然成功 |
| 模型返回 HTML/重定向 | 目标域名/路径、代理和部署区域访问是否正常 | 不把登录门户或 3xx 当成功 JSON，客户端不跟随重定向 |
| 结构化回答失败 | 截断、JSON 模式兼容性、输出预算、非法引用 | 不把模型原文直接保存为已验证答案 |
| 向量 degraded | 模型名、服务可达性、旧索引空间、响应维度 | 不把相同维度当模型兼容证明 |
| 索引长期等待/失败 | 当前单线程队列、后台日志、向量耗时、上次是否重启中断 | 不反复重启；自有书重建先确认清会话影响 |
| 有聊天记录但反馈报 404 | 回答是否已删、book/conversation/message 是否一致 | 不改 owner 校验以迁就过期页面 |
| 阅读器/批注 409 | 正文版本哈希或引用 anchor 失配：教材源文件更新过、索引与正文不一致 | 不改数据库强改批注；先重建索引或让用户重新打开阅读器 |
| 问答前出现多次检索、耗时变长 | qa 工具循环的正常行为；看回答下「模型自主检索 N 次」轨迹与 `agent_search` 日志 | 不把检索次数当故障；超预算调用会被自动拒绝并计入 warning 日志 |
| 统计表暂时为空 | 是否有归档、首窗口是否满 72 小时、是否检查失败 | 不改生产时间戳或手动重复运行应用工厂 |
| SQLite 锁或测试目录删不掉 | 是否有额外进程、索引/播种线程、未结束事务 | 不删 WAL、不在生产再起第二实例 |

应在实际部署区域核对外部服务：本机成功不证明 Railway 也能访问。记录真实状态码及脱敏错误，不在缺少证据时断言地域限制、网络代理或浏览器缓存是根因。

## 8. 定期维护清单

定期核对卷容量、可恢复备份、失败索引、反馈归档增长和模型额度；检查主备模型服务的数据授权及配置是否仍有效。每次教材/模型变更记录版本和潜在历史失效范围。

服务升级后分别记录静态复核、开发者测试和真实浏览器验收结果。文档更新不应附带未授权发布、注册、删除、数据库修复或配置变更。
